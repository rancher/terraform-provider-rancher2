## Abstract

This repository utilizes a **branch-based development release strategy** coordinated with automated backports and Release Please to manage stable SemVer versions on release branches (`release/v<major>`). Code is primarily developed and merged into the `main` branch, but all releases (both RCs and stable versions) are generated directly from the respective `release/v<major>` branch (e.g., `release/v15`, `release/v14`, `release/v13`).

---

## Technical Specification

### The 4-Step Release Lifecycle

Our release process follows a strict 4-step flow to ensure rigorous testing and stabilization before release:

1. **Development on `main`**: 
   - All feature work, bug fixes, and general development are merged into the default `main` branch via standard Pull Requests. Every PR is validated for issue linkage and passes the Nix container CI matrix before maintainers squash-merge it to trunk.

2. **Automated Backporting to Release Branches**:
   - Pushing the merge commit to `main` triggers `backport-prs.yml`.
   - The workflow queries open backport sub-issues associated with the PR, branches off each targeted release branch (e.g., `release/v15`), cherry-picks the commit (`git cherry-pick --allow-empty -x <sha> -X theirs`), and opens a Backport PR with auto-merge enabled.
   - Pre-merge acceptance testing is enforced on the Backport PR via `e2e-pr-listener.yml` and `e2e-pr.yml` in AWS prior to merging.

3. **Release Candidate (RC) Staging**:
   - When the backport PR merges into the release branch (`release/v*`), it triggers `release-please.yml` (which updates the pending `release-please` draft PR) followed by `release-branch-merge.yml`.
   - `release-branch-merge.yml` dynamically computes the next RC tag (e.g., `v15.2.0-rc.2`) using `computeNextRcTag` in `releases.js` and triggers `release.yml`.
   - `release.yml` pushes the RC tag, retrieves GPG signing credentials from HashiCorp Vault, builds and cryptographically signs binaries via GoReleaser (`.goreleaser_rc.yml`), and invokes `rc-notify` to comment on all qualifying `internal/backport` and `internal/merged` issues with the download link for QA verification.

4. **Production Release Publishing**:
   - The pending "Release PR" generated by Google's `release-please` acts as the gatekeeper for official stable releases.
   - Acceptance tests validate the `release-please` PR prior to merge via `e2e-pr.yml`.
   - **Only a human repository maintainer can merge the Release PR.**
   - Once a maintainer merges the Release PR into the release branch, `release-please.yml` triggers. Google's `release-please-action` outputs `release_created: true`, calling the unified `release.yml` via reusable workflow call (`workflow_call`) to retrieve Vault GPG credentials, compile and sign production binaries with GoReleaser (`.goreleaser.yml`), and promote the draft GitHub Release to published via `publish-release`.

## Standing Implementation Decisions

1. **Release Branch Authority**: Releases are exclusively cut from `release/v<major>` branches (e.g. `release/v15`). The `main` branch is used for development and staging backports, but no stable release artifacts are cut directly from `main`.
2. **Pre-Merge Acceptance Testing**: End-to-end acceptance tests run on automated PRs (both backport PRs and `release-please` PRs) *before* they are merged into release branches, ensuring that broken builds never compromise release branches.
3. **Unified Release Execution Workflow (`release.yml`)**: Release candidate and stable release generation are unified into `.github/workflows/release.yml`. This workflow guarantees consistent builds, GoReleaser configuration, Nix tooling, and Vault GPG signing across both automated triggers (`workflow_call` from `release-please.yml`) and manual triggers (`workflow_dispatch`).
4. **Targeted RC Notifications**: Release candidate notifications are integrated into `release.yml` via the `rc-notify` script. Upon completion of an RC release, it automatically discovers and comments on open issues associated with the release branch that have been marked `internal/backport` and `internal/merged`, ensuring immediate visibility for validation.
5. **Unified Release Workflow**: The single `release.yml` workflow serves as both an authenticated maintainer fallback (via `workflow_dispatch` for stable or RC tags) and the automated execution engine for `release-please.yml`.
