# Release Process: Branch-Based Releases

## Abstract

This repository utilizes a **branch-based development release strategy** coordinated with automated backports and Release Please to manage stable SemVer versions on release branches (`release/v<major>`). Code is primarily developed and merged into the `main` branch, but all releases (both RCs and stable versions) are generated directly from the respective `release/v<major>` branch.

---

## Technical Specification

### The 4-Step Release Lifecycle

Our release process follows a strict 4-step flow to ensure rigorous testing and stabilization before release:

1. **Development (`main` branch)**: 
   - All feature work, bug fixes, and general development are merged into the `main` branch via standard Pull Requests.

2. **Automated Backporting**:
   - When a PR is merged into `main`, an automated workflow triggers to cherry-pick those changes into the targeted release branch (e.g., `release/v15.2.0`), creating a "backport PR".

3. **Release Candidate (RC) Generation**:
   - When the backport PR is approved and merged into the release branch (`release/v*`), it triggers `.github/workflows/release-branch-merge.yml`.
   - This workflow dynamically computes the next RC tag (e.g., `v15.2.0-rc.2`) and triggers the unified `rc-release.yml` workflow to build, sign, and push the Release Candidate artifacts.
   - Concurrently, `release-please` runs against the release branch and either creates or updates a pending "Release PR" containing the changelog and version bump.

4. **Stable Release Generation**:
   - The pending "Release PR" generated by `release-please` acts as the gatekeeper for a stable release.
   - **Only a human user can merge the Release PR.**
   - Once a maintainer merges the Release PR into the release branch, the `release.yml` workflow triggers. It executes a full suite of end-to-end acceptance tests, and upon success, generates the final stable release artifacts, signs them, and publishes the official GitHub Release.

---

## Standing Implementation Decisions

1. **Release Branch Authority**: Releases are exclusively cut from `release/v<major>` branches. The `main` branch is used for development and staging backports, but no stable release artifacts are cut directly from `main`.
2. **Unified RC Release Workflow (`rc-release.yml`)**: Release candidate generation is unified into `.github/workflows/rc-release.yml`. This workflow guarantees consistent builds, GoReleaser configuration, Nix tooling, and Vault GPG signing. 
3. **Targeted RC Notifications**: Release candidate notifications are integrated into `rc-release.yml` via the `rc-notify` script. Upon completion of an RC release, it automatically discovers and comments on open issues associated with the release branch that have been marked `internal/backport` and `internal/merged`, ensuring immediate visibility for validation.
4. **Manual Full Release Publishing**: The manual full release workflow (`manual-release.yml`) serves as a fallback to build draft releases with GoReleaser. To finalize these, the workflow automatically invokes the `publish-release` script to promote the draft release to published.
